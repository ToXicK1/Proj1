# Rebuild Technical Decisions

Earlier decisions remain in `docs/DECISIONS.md` (ADR-001 to ADR-055). Rebuild decisions are numbered RD-n. RD-1 to RD-8 were answered on 2026-11-19.

| ID | Decision | Status | Rationale |
|---|---|---|---|
| RD-1 (D1) | Default lifecycle follows the rebuild prompt's department stage lists; AWS 33-stage lifecycle kept as an importable template; AWS scopes become applicability profiles | Accepted | The prompt is explicit and says not to copy the AWS lifecycle blindly |
| RD-2 (D2) | Only the assigned human professional gives final approval. The owner sees the work and gives input to that professional, who reviews it and decides what to send to the AI. The prompt's user approval stages become owner input steps | Accepted (user's own model, not the recommendation) | Keeps one accountable approver per department while keeping the owner involved |
| RD-3 (D3) | Evolve the modular monolith | Accepted (default) | Core modules are tested and sound |
| RD-4 (D4) | PostgreSQL job queue and a worker process | Accepted | Durable, transactional with state, no new service |
| RD-5 (D5) | MinIO for files and large artifacts. **Amended 2026-11-20:** any S3-compatible store; locally SeaweedFS 3.80 | Accepted, amended | S3-compatible locally and in production. MinIO no longer publishes public container images (`minio/minio` and `quay.io/minio/minio` both refuse pulls), so the local stack runs SeaweedFS (Apache-2.0) behind the same S3 API. The platform's client speaks plain S3 (SigV4), so MinIO, S3 or another store can replace it by configuration |
| RD-6 (D6) | Tailwind during the workspace rebuild | Accepted (default) | Prompt default; pages are being rebuilt anyway |
| RD-7 (D7) | Local Ollama for the first end-to-end proof; cloud key later | Accepted (default) | No credentials needed now |
| RD-8 (D8) | Commit the current tree to main and push as the baseline | Accepted (user chose main and push) | Protects existing work |
| RD-9 | Agents never call each other; the orchestrator routes all collaboration | Proposed | AWS principle, keeps every exchange recorded and permission-checked |
| RD-10 | Conditions are deterministic expressions, never model text | Proposed | The engine must decide transitions |
| RD-11 | Mandatory design system: forest green identity, beige workspaces, electric purple for AI and accents, separate status colours, central tokens (`docs/architecture/DESIGN_SYSTEM.md`) | Accepted (your specification) | Applies to every page and replaces Tailwind-first styling in RD-6: Tailwind, if added, must read these tokens |
| RD-12 | Inside a department, the professional approves every AI step and also the department package at Human Professional Review | Accepted (2026-11-20, Phase 7 Q1) | Strictest governance; keeps HUMAN_REVIEW_ARCHITECTURE.md as written |
| RD-13 | Solution Architect and UI/UX Designer run in parallel once the BA package is approved | Accepted (Phase 7 Q2) | Both depend only on the BA package; uses the Phase 5 parallel engine |
| RD-14 | The department lifecycle becomes the default only when all six departments are built and tested | Accepted (Phase 7 Q3) | New projects never stop part-way through an unfinished lifecycle |

| RD-15 | AI spending controls before Phase 7. The platform keeps a price list: Claude's published list prices as defaults, and administrators can override any price. Budgets are monthly, for the organization and per project. Each sends a warning at a set percentage, and at the limit either pauses AI work or continues on free providers only. A provider that runs out of credit is skipped until next month; one whose key is refused is skipped until the key is replaced; rate limits and outages get a short cooldown. Each route can try providers in order or cheapest first | Accepted (2026-11-23, your request) | Keeps an API bill under a set limit, and fails over to another provider (Claude, OpenAI, Gemini or local) automatically, without anyone watching. Enforced on the server before every call |
| RD-16 | The Claude adapter stays on direct HTTP (httpx) rather than the official `anthropic` SDK | Accepted (deviation from the SDK recommendation; for your review) | Every adapter shares one httpx client so tests can mock vendor HTTP with `httpx.MockTransport`, and the current SDK moved to a different HTTP library. The adapter follows the documented Messages API: prompt caching, adaptive thinking with summaries, tools with native block replay, streaming events, refusals, and spend-cap and billing errors. Moving to the SDK later changes only `AnthropicAdapter` |
| RD-17 | Department working objects are versioned work records; what is approved is a package that snapshots exact record versions; AI only proposes records (`WORKSPACES_PLAN.md` §2) | Proposed | Lets professionals edit one requirement or test case while approvals stay bound to immutable versions and the AI never commits state |
| RD-18 | Workspaces: in-house design canvas plus Figma; platform repository plus GitHub App; local Docker preview environment as staging, production unconfigured; built department by department after a shared core | Accepted (2026-11-23, D1–D4) | Your answers; outside connections only with your own accounts and authorization |
| RD-19 | Who approves a department package. A package with only AI content and the professional's confirmations can be approved by the department's assigned professional. If it contains that person's own edits, another assigned professional of the department must approve it. With nobody else assigned, administrators are notified to assign a second reviewer. Confirming a suggestion, or changing only its provenance, does not count as an edit | Accepted (2026-11-23, your answer) | Keeps the engine's separation-of-duties rule (nobody approves content they wrote) while one professional per department can still approve AI work |
| RD-20 | The Project Manager is the seventh professional profile, with its own workspace, AI persona and approvals; it coordinates but cannot override specialist decisions (security, architecture, QA results, release). The organization role `project_manager` stays for organization-wide oversight (`PM_CLIENT_ARCHITECTURE.md`) | Accepted (2026-11-24, your clarification) | A real software organization: the PM owns the client relationship and delivery, the departments own their disciplines |
| RD-21 | Discovery is PM-led. The PM records client meetings, validates the intake and approves the Project Brief before the BA starts. The client's 8-question form becomes an optional pre-meeting input (D3) | Accepted (D3) | The client meets the PM in person; AI structures, the PM decides |
| RD-2 (amended 2026-11-24) | The client gives a second, required approval on chosen items: the BRD baseline, design sign-off, UAT and milestones, after the professional's. Elsewhere the client gives input only | Accepted (D1) | The client owns the business baseline; the professionals stay accountable for their work |
| RD-22 (amended 2026-11-24) | The administrator creates every account (client, PM, professionals) with one of the platform's roles and a generated temporary password, shown once and expiring after 7 days, which must be changed at first sign-in. The administrator also creates projects and assigns people to them. Self-signup is off; the PM does not invite anyone | Accepted (your change to D2) | One accountable place for identities, roles and project membership; no self-service accounts |
| RD-23 | One client project assistant, with client-safe context only, replaces the per-department representatives (D4) | Accepted | One clear voice for the client; decisions route to the PM |
| RD-24 | Delivery is baseline, then sprints: each approved sprint plan starts its own sprint workflow, and DevOps has a continuous track (D5) | Accepted | Iterative delivery without losing the governed baseline |
| RD-25 | PM and client alignment (P1 to P8) is built before the remaining Phase 7 work (D6) | Accepted | Later departments are built sprint-aware from the start |
