Proj1 · AI-DLC platform

How the AI-DLC platform is built

A software-delivery platform where AI agents draft the work of each department (business analysis, architecture, design, development, QA, DevOps) and named human professionals approve every step. This guide explains every technology, every service and the main code paths.

~20,700lines of Python ~8,900lines of TypeScript 35database migrations 57backend test files 8Docker services

The big picture

Three ideas explain almost every design choice in the code.

1. Humans decide, AI proposes. AI agents produce drafts (requirements, designs, code). They can never move a workflow stage, approve anything, or change protected state. Only a person holding the right profile approves, and the approval is tied to the exact version they looked at.
2. Everything is recorded. Every stage output is a new immutable version. Every important action goes into a tamper-evident audit chain (each event hashes the one before it). Agent runs record which sources they were given.
3. Code never runs on the server. Building, testing, git and the terminal all run in a fresh, locked-down Docker container started by one dedicated service, the executor. The API and the worker only queue jobs and read results.

Architecturally it is a modular monolith (RD-3): one FastAPI codebase split into domain packages, sharing one PostgreSQL database. It is deployed as several processes from the same image: the API, a background worker and the executor. That keeps transactions simple (state and the job queue live in the same database) while keeping the dangerous parts separate.

Engine and governance

The heart of the platform: how work moves, who may move it, and how that is proven afterwards.

Stage state machine

workflows/state_machine.py

Pure logic, no database. Each stage is in one of 15 states: NOT_STARTED → READY → RUNNING → AI_COMPLETED → VALIDATING → AWAITING_HUMAN_REVIEW → APPROVED, plus CHANGES_REQUESTED, AWAITING_USER_INPUT, BLOCKED, FAILED and others.

Every legal edge lists the actor types allowed to take it: human, system, ai_agent, provider. AI agents and providers appear in no allow-list, so they can never move a stage.

Workflow compiler

workflows/compiler.py · seed.py · studio/

Workflows are YAML: stages, dependencies, the agent or task each runs, approval policy, conditions. The compiler validates and freezes them into a definition the engine executes. Parallel branches are supported (the Architect and the Designer work at the same time after the BA, RD-13).

The Studio edits a draft; publishing creates an immutable version, so running projects never change underneath.

Conditions

workflows/conditions.py

Whether a stage applies is decided by structured, deterministic expressions over project facts, never by model text and never by code (RD-10). The same input always gives the same route.

Engine service

workflows/service.py (990 lines)

The only writer of stage state. It starts ready stages, queues AI work, runs validations, opens approvals, and advances when every gate is clear. Everything else asks it.

Approvals

approvals/policy.py · service.py

A policy (single, all-of, sequential…) becomes slots. Each slot names who may fill it (a project role or profile:business_analyst) and how many distinct people it needs.

  • Bound to the exact artifact version judged: a new version makes the approval stale.
  • Enforced on the server, never only in the UI.
  • Nobody approves their own work; your own edits need a second reviewer (RD-19).
  • The client gives a second sign-off on the BRD baseline, design and UAT (RD-2 amended).

Audit chain

audit/service.py

Each event stores prev_hash and hash = SHA-256(prev_hash + canonical JSON), one chain per organization. verify_chain recomputes the chain; any edited or deleted row breaks it. Tamper-evident, like a small blockchain without the consensus.

Sensors

sensors/registry.py · service.py

Deterministic checks (pure functions, no AI, no database) run against artifact versions: required sections present, traceability, and similar. A gate clears only on real results. A failing sensor can be accepted as a risk by a person, and that acceptance is recorded.

Hooks and rules

hooks/ · rules/

Hooks are declarative: a hook picks one built-in action (notify, require a check…) and can never run code. Rules are hierarchical instructions (platform, organization, project). Lessons the AI proposes become rules only after a person approves them.

AI layer

Agents and profiles

agents/service.py · models.py

A profile is a professional role (Business Analyst, Solution Architect, UX Designer, Developer, QA, DevOps, Project Manager). An agent has immutable versions: prompt, model route, allowed context sources, tool grants. A run always records which version it used.

Lead and reviewer runner

agents/runner.py

The lead agent gets only the sources its version allows. A reviewer agent gets only the artifact, never the input or the lead's reasoning, so its review is independent. Each run stores a manifest of sources (IDs and counts, never content).

Tools and the registry

agents/tool_runtime.py · tools/definitions.py · registry.py

Tool definitions live in reviewed code and are mirrored into tool_registry at start-up. A grant must match the agent's department and the tool must be enabled; an admin disabling a tool takes effect at run time. Today's agent tools are read-only. The code tools (repo_commit, run_checks) become grantable to the Developer agent in Phase 2e, and even then they only work on the agent's own branch.

Providers and adapters

providers/adapters.py · base.py · routing.py

One adapter per vendor: Anthropic Messages API, OpenAI, Gemini, any OpenAI-compatible server (Ollama, vLLM) and a deterministic offline mock (refused outside dev and test). Adapters are the only code that knows vendor formats. Routing chooses which model a kind of task uses, optionally per department.

Keys and spend

providers/secrets.py · costs.py · spend.py

API keys are sealed with AES-256-GCM (fresh nonce, organization-bound associated data); only the last four characters are ever shown. Money is stored as integer micro-dollars. Monthly budgets for the organization and per project warn at a set percentage and, at the limit, pause AI or fall back to free providers (RD-15).

Assistants

work/assistant.py · work/pm_analysis.py · portal/client_assistant.py

Each department has an AI assistant that proposes records. The PM's persona analyses client meetings. The client has one assistant that sees client-safe context only (RD-23). All of them propose; a person decides.

The AI's output enters the system as a proposal (a draft record or a new artifact version). Only a human action or the engine's deterministic rules turn it into approved state.

Running code safely

The newest part of the system (Phases 1 and 2). Everything here exists so that the Developer IDE and, later, the Developer AI can build, test and commit real code.

Executor

execution/executor.py · RD-30

The only service with the Docker socket. It gets only the database URL and the runner image name, with no .env and no secrets. It polls execution_jobs, re-validates each job, and decides the image and command itself from the job's kind.

Each job gets a fresh container: no network, read-only root, all capabilities dropped (except three used to drop privileges), 768 MB, 1 CPU, 128 processes, a time limit, and a throwaway /job volume. The result is read after the marker @@AIDLC-RESULT@@, and the container is always removed.

Runner image and job scripts

infrastructure/docker/runner.Dockerfile · sandbox/job.py · gitjob.py · terminal_init.py

Python 3.12 slim with pytest, Node.js and git. job.py builds and runs tests. gitjob.py runs git as uid 2000 on a copy of the repository; only writes are copied back, through tar's safe data filter, under a per-project lock. terminal_init.py prepares a terminal's working copy.

Repositories and change sets

repos/service.py

Each project gets a bare git repository on the repos volume. The rules:

  • No direct commits to main; work happens on branches.
  • A change set (like a pull request) is approved by an engineer other than its author, at a specific commit (reviewed_sha).
  • A new commit makes the approval stale. The merge happens only at the approved commit.
  • This service decides and records; every git command is an executor job.

IDE terminal (Phase 2d)

terminal/ · execution/terminal_server.py · ide/TerminalPanel.tsx

Browser xterm.js → API WebSocket → executor's internal server on port 8090, which is never published. The API checks the origin, the signed-in person, their engineering profile and that the session is theirs. It then passes a one-time nonce (valid for two minutes, used once) that the browser never sees.

The shell runs as uid 2000 in its own container with no network. Every typed line and the last 200 KB of output are recorded. The session ends after 10 idle minutes or 30 minutes in all.

Two queues, on purpose

jobs/ (worker) · execution/ (executor)

jobs is the worker's queue for AI and system work. Workers claim with FOR UPDATE SKIP LOCKED under a lease kept alive by a heartbeat; if a worker dies, another takes the job (at-least-once, so handlers are idempotent). execution_jobs is separate so that code execution has its own isolated consumer.

Live events

events/service.py · router.py · workspace/liveEvents.tsx

Services publish to workspace_events (commits, reviews, builds, terminal sessions). The browser follows a WebSocket at /api/v1/projects/{id}/events/ws, authenticated by cookie, origin-checked and re-authorised on each poll. After a reconnect it catches up over REST from the last event it saw.

Data and migrations

One PostgreSQL database holds everything. app/models.py imports every model so Base.metadata is complete for Alembic and for the drift test. Notable patterns:

  • Immutable versions: artifacts, agent versions, skill versions, published workflows and work-record versions are never edited in place. A change writes a new row.
  • Packages snapshot versions (RD-17): what a department hands off is a package pointing to exact record versions, so approval binds to precisely what was reviewed.
  • UUIDv7 keys (uuid7() in core/db.py): unique like UUIDs but time-ordered, so indexes stay efficient.
  • JSON columns for flexible bodies (record fields, limits, terminal inputs), with fixed columns for everything that is queried or governed.
  • Money as integers: micro-dollars, converted to numbers only at the API edge (the cause of the spend-panel fix).

Authentication is a server-side session in an HttpOnly cookie. The browser never holds a bearer token. State-changing requests carry an X-CSRF-Token header, computed as an HMAC of the session, so nothing extra is stored.

Request walkthroughs

Follow a real action through every layer.

  1. The engine starts the stage.workflows/service.py
    Dependencies are approved and the conditions say it applies, so it moves READY → RUNNING as the system actor and enqueues a job.
  2. The worker claims the job.jobs/service.py · worker.py
    SELECT … FOR UPDATE SKIP LOCKED, under a lease.
  3. The agent runs.agents/runner.py · providers/
    Its version decides the prompt, the allowed sources and the model route. The budget is checked, the adapter calls the vendor, spend is recorded, and the output is saved as a new artifact version.
  4. Validation.sensors/
    Deterministic sensors check the version. The stage goes to AWAITING_HUMAN_REVIEW with an approval opened for that exact version.
  5. A person approves.approvals/service.py
    The professional with the right profile approves. The server checks the slot, independence and the version. The decision is written to the audit chain.
  6. The engine advances.workflows/service.py
    All slots are filled, so the stage is APPROVED and its dependants become READY.
  1. The developer clicks "Build and test".ide/IdePage.tsx
    The files on screen, unsaved edits included, are sent to POST /executions.
  2. The API checks and queues.execution/service.py
    The caller must be an engineering professional or an admin. Only the kind checks is allowed publicly. A row is inserted in execution_jobs. Nothing runs in the API.
  3. The executor takes it.execution/executor.py
    It re-validates the job, chooses the image and command, creates a locked-down container and puts the files in /job.
  4. The tests run.sandbox/job.py
    The job builds and runs pytest (or Node tests) as an unprivileged user, with no network, and prints the result after the marker.
  5. Clean-up and result.executor.py
    The container and its volume are removed. The result is stored and an event is published.
  6. The IDE shows it.liveEvents.tsx
    The live event (or polling) updates Output, Problems and the status bar.
  1. Commit on a branch.repos/service.py → gitjob.py
    Commits to main are refused. The commit runs as a git executor job.
  2. Open a change set.
    The diff between the merge base and the head is computed by another job and shown in Monaco's diff editor.
  3. Review.
    Another engineer approves at the head commit. The author trying to approve gets "You cannot approve your own change set".
  4. Stale check.
    Any new commit after approval makes it stale; it must be reviewed again.
  5. Merge.
    The merge job checks that the branch head still equals the approved SHA, then merges. Every step is audited and shown live.
  1. Open.POST /terminal
    Permission, repository and branch are checked. A session row with a random nonce is created and audited.
  2. Connect.terminal/router.py
    The browser opens the WebSocket. The API checks the origin, the cookie, the person and the session owner, then connects to ws://executor:8090 with the nonce in a header.
  3. Claim.terminal_server.claim
    The executor locks the row, checks the nonce and its age, clears the nonce and marks the session running.
  4. Container.
    A fresh runner container clones the branch into /work/project as uid 2000, with no network.
  5. Shell.
    bash -l with a TTY. Keystrokes and output are relayed; each line is recorded.
  6. End.
    On idle, time limit, close or disconnect, the container is removed and the record is finished with its transcript.

Security model

ThreatControl in the code
Stolen passwordArgon2id, lockout and rate limits, timing-equalised unknown emails, forced change of temporary passwords.
Session theft, CSRFServer-side sessions in an HttpOnly cookie; an HMAC CSRF token on every state change; origin checks on WebSockets.
Leaked API keysAES-GCM sealed in the database, never sent to the frontend, never committed; only the last four characters are shown.
AI overreachNo actor type for AI on any state edge; read-only tools; grants scoped by department and enabled flag; reviewers isolated from leads.
Approval tamperingApprovals bound to versions or commits; independence rules; server-side only; audited in a hash chain.
Malicious codeContainer per job, no network, read-only root, dropped capabilities, resource limits, unprivileged user, no secrets in the environment.
Path or archive tricksSafe path checks in the API and IDE; tar extracted with the data filter; branch names checked with a strict pattern.
Data leaking to clientsThe portal builds every response field by field from an allow-list; the client assistant gets client-safe context only.
Untrusted external contentTreated as data: owner messages are classified deterministically, and free text selects a category and nothing else.

Testing

  • Backend: backend/tests/, 57 files with pytest against a real PostgreSQL (pgserver). Docker and AI vendors are faked at their boundaries (FakeDocker, FakeGit, httpx.MockTransport), and the real paths are proven on the test stack. The last full run before Phase 2d passed 557 tests. Phase 2d added 5 terminal tests, which pass. The full suite has not been re-run since.
  • Frontend unit: Vitest with Testing Library, 23 tests (paths, graph, live events, steps, API helper, UI).
  • Browser end to end: Playwright in tests/e2e/ against the isolated aidlc-e2e stack. The IDE spec edits code, builds and tests in a real container, commits, opens a change set, checks that self-approval is refused, and runs a real terminal (ls, uid 2000, no network).
  • Lint and types: Ruff for Python, tsc --noEmit before every frontend build.

How to study the code

An order that builds understanding layer by layer. Read the module docstrings first: each file starts with a summary of what it does and what it guarantees.

  1. docker-compose.yml: what runs, and with which permissions.
  2. backend/app/main.py and core/: how the app is assembled, configured and secured.
  3. auth/service.py, auth/deps.py: who the caller is on every request.
  4. workflows/state_machine.py, then compiler.py and conditions.py: the rules of motion.
  5. workflows/service.py: the engine. The longest and most important file.
  6. approvals/policy.py and approvals/service.py: how humans gate it.
  7. audit/service.py: the hash chain, short and elegant.
  8. agents/runner.py, providers/adapters.py, providers/secrets.py: how AI is called and contained.
  9. jobs/service.py, worker.py: the durable queue.
  10. work/service.py and portal/lifecycle.py: departments, records and the 33-stage lifecycle.
  11. execution/executor.py, sandbox/job.py, repos/service.py, terminal_server.py: running code safely.
  12. frontend/src/App.tsx, api.ts, workspace/modules.ts, then ide/IdePage.tsx: the UI from routes down.
  13. docs/rebuild/TECHNICAL_DECISIONS.md (RD-1 to RD-30): the reasons behind everything above.
